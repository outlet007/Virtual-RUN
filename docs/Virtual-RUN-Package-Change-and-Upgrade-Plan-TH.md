# Virtual RUN — แผนระบบเปลี่ยนและอัปเกรดแพ็กเกจ

วันที่จัดทำ: 2026-10-08 (Asia/Bangkok)

สถานะเอกสาร: แผนสำหรับพัฒนาในอนาคต ยังไม่มีการแก้ไขโค้ดหรือฐานข้อมูลตามเอกสารนี้

## 1. วัตถุประสงค์

กำหนดกติกาการสมัครแพ็กเกจให้ชัดเจนสำหรับงานวิ่งที่มีหลายแพ็กเกจ โดยแยกกรณีงานฟรี งานเสียเงินที่ยังรอชำระ และงานเสียเงินที่ยืนยันการชำระแล้ว เพื่อให้ผู้ใช้เปลี่ยนใจได้ในช่วงที่เหมาะสม โดยไม่ทำให้ยอดเงิน ใบสมัคร BIB ผลวิ่ง เหรียญ และการจัดส่งไม่ตรงกัน

## 2. สถานะระบบปัจจุบัน

- `registrations` ป้องกันการสมัครซ้ำด้วย `unique (user_id, package_id)` จึงยังอนุญาตให้ผู้ใช้คนเดียวสมัครหลายแพ็กเกจในงานเดียวกันได้
- งานฟรีสร้างใบสมัครเป็น `confirmed` ทันที
- งานเสียเงินสร้างใบสมัครเป็น `pending` และสร้าง `payments` สถานะ `pending`
- `payments` รองรับสถานะ `pending`, `paid` และ `failed` แต่ยังไม่มี `cancelled`
- หนึ่งใบสมัครมีรายการชำระเงินได้หนึ่งรายการตาม unique index ของ `payments.registration_id`
- เมื่อ Admin ยืนยันการชำระ ระบบเปลี่ยน Payment เป็น `paid` และ Registration เป็น `confirmed`
- เมื่อ Admin ปฏิเสธ ระบบเปลี่ยน Payment เป็น `failed` และ Registration เป็น `cancelled`
- ผลวิ่งผูกกับ `registration_id` ส่วนเป้าหมายระยะวิ่งมาจากแพ็กเกจของใบสมัคร
- เมื่อเปิดใช้ Strava หากกิจกรรมตรงกับหลายใบสมัคร ระบบจะไม่เลือกให้อัตโนมัติ แต่พักกิจกรรมไว้ให้ผู้ใช้เลือก

## 3. คำศัพท์ที่ใช้ในแผน

- **เปลี่ยนแพ็กเกจ (Change package):** ยกเลิกใบสมัครงานเสียเงินที่ยังรอชำระ แล้วสมัครแพ็กเกจใหม่ โดยยังไม่มีสิทธิ์วิ่งจากใบสมัครเดิม
- **อัปเกรดแพ็กเกจ (Upgrade package):** เปลี่ยนแพ็กเกจของใบสมัครงานฟรีที่ยืนยันแล้วไปยังเป้าหมายระยะสูงขึ้น โดยรักษาใบสมัคร BIB และผลวิ่งสะสมเดิม
- **ลดระดับ (Downgrade):** เปลี่ยนจากเป้าหมายระยะสูงไปต่ำ ไม่อยู่ในขอบเขตที่แนะนำ
- **ใบสมัครที่ใช้งานอยู่:** ใบสมัครสถานะ `pending` หรือ `confirmed`; ใบสมัคร `cancelled` ไม่ถือว่าใช้งานอยู่

## 4. นโยบายที่แนะนำ

### 4.1 งานฟรี

- อนุญาตให้อัปเกรดได้เฉพาะแพ็กเกจที่มีระยะเป้าหมายสูงกว่า
- แพ็กเกจใหม่ต้องอยู่ในงานเดียวกัน
- งานต้องยังเปิดรับสมัครและยังไม่พ้นวันสิ้นสุดตามเวลา Asia/Bangkok
- ใช้ `registration_id` และ BIB เดิม
- เก็บผลวิ่งสะสมเดิมทั้งหมด
- ไม่สร้าง Payment
- ไม่อนุญาตให้ลดระยะ
- ไม่อนุญาตหากเริ่มกระบวนการจัดส่งรางวัลหรือเหรียญที่ขัดกับแพ็กเกจใหม่แล้ว
- หลังอัปเกรดต้องคำนวณสถานะความสำเร็จ เหรียญ และรางวัลใหม่อย่างปลอดภัยและไม่ให้รางวัลซ้ำ

ตัวอย่าง: ผู้ใช้สมัคร 10 กม. และสะสมได้ 7 กม. เมื่ออัปเกรดเป็น 21 กม. ระบบต้องแสดงความคืบหน้า 7/21 กม. โดยไม่ลบผลเดิม

### 4.2 งานเสียเงินที่ยังรอชำระ

- ผู้ใช้ควรยกเลิกหรือเปลี่ยนใจได้เองตราบใดที่ Registration และ Payment ยังเป็น `pending`
- การเปลี่ยนแพ็กเกจไม่ใช่การอัปเดตราคาใน Payment เดิม แต่ให้ยกเลิกใบสมัครและ Payment เดิม แล้วสร้างใบสมัครและ Payment ใหม่ผ่านขั้นตอนสมัครมาตรฐาน
- การยกเลิกและการสมัครใหม่ต้องเป็นรายการที่ตรวจสอบย้อนหลังได้
- เมื่อยกเลิกสำเร็จ ผู้ใช้จึงเลือกแพ็กเกจใหม่และได้รับยอดเงินกับเลขอ้างอิงใหม่
- ถ้างานปิดรับสมัครระหว่างการยกเลิก ผู้ใช้จะสมัครแพ็กเกจใหม่ไม่ได้ จึงต้องแสดงคำเตือนก่อนยืนยันการยกเลิก
- การยกเลิกต้องล็อกแถวและทำแบบ transaction เพื่อป้องกันชนกับการที่ Admin กำลังยืนยันการชำระพร้อมกัน

### 4.3 งานเสียเงินที่ยืนยันแล้ว

- ไม่อนุญาตให้อัปเกรดแพ็กเกจด้วยตนเองในระยะแรก
- ไม่เพิ่มระบบชำระค่าส่วนต่าง
- หากจำเป็นต้องแก้ไข ให้เป็นกระบวนการพิเศษของ Admin พร้อมบันทึกเหตุผล ไม่ใช่การแก้ `package_id` โดยตรงโดยไม่มีประวัติ

## 5. ตารางสิทธิ์ที่เสนอ

| ประเภทงาน | Registration | Payment | การกระทำของผู้ใช้ |
|---|---|---|---|
| ฟรี | `confirmed` | ไม่มี | อัปเกรดไประยะสูงกว่าได้ |
| เสียเงิน | `pending` | `pending` | ยกเลิกเองหรือเปลี่ยนแพ็กเกจได้ |
| เสียเงิน | `confirmed` | `paid` | เปลี่ยนหรืออัปเกรดเองไม่ได้ |
| เสียเงิน | `cancelled` | `failed`/`cancelled` | สมัครใหม่ได้ถ้างานยังเปิด |
| ทุกประเภท | งานหมดเวลา/ปิดรับสมัคร | ทุกสถานะ | ไม่เริ่มการเปลี่ยนหรืออัปเกรดใหม่ |

## 6. ประสบการณ์ผู้ใช้ที่เสนอ

### หน้ารอชำระเงิน

แสดงปุ่ม:

- `ชำระเงิน`
- `เปลี่ยนแพ็กเกจ`
- `ยกเลิกการสมัคร`

เมื่อกด `เปลี่ยนแพ็กเกจ` ให้แจ้งว่า:

> ระบบจะยกเลิกรายการชำระเงินเดิม และสร้างใบสมัครกับยอดชำระเงินใหม่ตามแพ็กเกจที่เลือก เลขอ้างอิงเดิมจะใช้ไม่ได้

หลังยืนยัน:

1. เรียก RPC ยกเลิกรายการเดิม
2. กลับไปหน้าเลือกแพ็กเกจของงาน
3. แสดงแพ็กเกจเดิมว่า `ยกเลิกแล้ว` ได้ในประวัติ แต่ไม่ถือว่าเป็นใบสมัครที่ใช้งานอยู่
4. ผู้ใช้สมัครแพ็กเกจใหม่ผ่าน `register_for_event`

### หน้าใบสมัครงานฟรี

- แสดง `อัปเกรดระยะ` เมื่อมีแพ็กเกจระยะสูงกว่าและผ่านเงื่อนไข
- แสดงระยะเดิม ระยะใหม่ และผลวิ่งสะสมที่จะถูกเก็บไว้
- ขอการยืนยันก่อนเปลี่ยน
- หลังสำเร็จ แสดงเป้าหมายใหม่ทันที

## 7. ผลกระทบต่อ Supabase และ Migration

ต้องสร้าง Migration ใหม่ ไม่แก้ไข Migration เก่า และไม่ต้องติดตั้ง Supabase ใหม่

### 7.1 สถานะ Payment

เพิ่ม `cancelled` ใน check constraint ของ `payments.status` เพื่อแยกกรณีผู้ใช้ยกเลิกเองออกจาก `failed` ซึ่งควรใช้กับการชำระที่ถูกปฏิเสธหรือไม่สำเร็จ

### 7.2 RPC ยกเลิกใบสมัครที่รอชำระ

เพิ่ม RPC เช่น `cancel_pending_registration(p_registration_id uuid)` โดยต้อง:

- ใช้ `auth.uid()` ตรวจเจ้าของใบสมัคร
- ล็อก Registration และ Payment ด้วย `FOR UPDATE`
- ยอมรับเฉพาะ Registration=`pending` และ Payment=`pending`
- ปฏิเสธทันทีหาก Admin ยืนยันหรือปฏิเสธไปแล้ว
- เปลี่ยน Registration เป็น `cancelled`
- เปลี่ยน Payment เป็น `cancelled`
- ทำทั้งหมดใน transaction เดียว
- จำกัดสิทธิ์ `EXECUTE` เฉพาะ `authenticated`
- ไม่เปิดสิทธิ์ update ตารางโดยตรงให้ผู้ใช้

### 7.3 RPC อัปเกรดงานฟรี

เพิ่ม RPC เช่น `upgrade_free_registration(p_registration_id uuid, p_target_package_id uuid)` โดยต้อง:

- ตรวจเจ้าของด้วย `auth.uid()`
- ล็อกข้อมูลที่เกี่ยวข้องก่อนตรวจและเปลี่ยน
- Registration ต้องเป็น `confirmed`
- Event ต้องเป็นงานฟรี เปิดรับสมัคร และยังไม่หมดเวลา
- แพ็กเกจเดิมและใหม่ต้องอยู่ใน Event เดียวกัน
- ระยะเป้าหมายใหม่ต้องมากกว่าเดิม
- ต้องไม่มี Payment ของใบสมัครนี้
- ต้องผ่านกติกาเหรียญและการจัดส่ง
- เปลี่ยนเฉพาะ `package_id` โดยรักษา `registration_id`, BIB และ Submissions เดิม
- บันทึกประวัติการอัปเกรด

### 7.4 ประวัติการอัปเกรด

แนะนำเพิ่มตาราง `registration_package_upgrades` อย่างน้อยประกอบด้วย:

- `id`
- `registration_id`
- `user_id`
- `from_package_id`
- `to_package_id`
- `upgrade_type` เช่น `free_distance_upgrade`
- `created_at`

เปิด RLS และให้ผู้ใช้อ่านเฉพาะประวัติของตนเอง ส่วนการเขียนให้ทำผ่าน RPC เท่านั้น

### 7.5 หนึ่งใบสมัครที่ใช้งานอยู่ต่อหนึ่งงาน

เป้าหมายระยะยาวคือผู้ใช้หนึ่งคนมีใบสมัครที่ใช้งานอยู่ได้หนึ่งใบต่อ Event แต่ต้องตรวจข้อมูลจริงก่อนเพิ่ม unique constraint เพราะระบบปัจจุบันอาจมีผู้ใช้หลายแพ็กเกจในงานเดียวกันแล้ว

ควรพิจารณา partial unique index ที่ไม่นับ `cancelled` แทน `unique (user_id, event_id)` แบบตายตัว เพื่อให้ผู้ใช้ยกเลิกแล้วสมัครใหม่ได้ เช่นแนวคิด:

```sql
create unique index ...
on public.registrations (user_id, event_id)
where status in ('pending', 'confirmed');
```

ต้องวิเคราะห์ผลของการเปลี่ยนสถานะและข้อมูลซ้ำก่อนเขียน Migration จริง

## 8. ผลกระทบต่อส่วนอื่น

- **Payment:** งานเสียเงินที่ยืนยันแล้วไม่เปลี่ยนพฤติกรรม; เพิ่มเฉพาะการยกเลิก Payment ที่ยัง pending
- **ผลวิ่ง:** งานฟรีที่อัปเกรดใช้ registration เดิม จึงเก็บผลสะสมเดิมได้
- **BIB:** งานฟรีที่อัปเกรดใช้ BIB เดิม; ใบสมัครเสียเงินที่ยกเลิกยังไม่มี BIB เพราะยังไม่ confirmed
- **Strava:** การบังคับหนึ่งใบสมัครที่ใช้งานอยู่ต่อ Event ช่วยลดกรณีกิจกรรมตรงหลายใบสมัคร แต่ยังต้องทดสอบกรณีผู้ใช้เข้าร่วมหลาย Event ที่ช่วงวันทับกัน
- **เหรียญดิจิทัลและรางวัล:** ต้องคำนวณสิทธิ์ใหม่หลังอัปเกรดและป้องกันการให้ซ้ำ
- **เหรียญจริงและการจัดส่ง:** ต้องห้ามหรือส่งให้ Admin ตรวจถ้าการจัดส่งเริ่มแล้ว
- **Admin:** ต้องแสดงเหตุผลการยกเลิกและประวัติการอัปเกรดได้
- **รายงาน:** ต้องกำหนดว่ารายการ `cancelled` นับในยอดสมัครทั้งหมดหรือแยกเป็นยอดยกเลิก

## 9. กรณีพิเศษที่ต้องตัดสินใจก่อนพัฒนา

1. งานฟรีแต่แพ็กเกจมีเหรียญจริงต่างกัน จะให้เปลี่ยนก่อนเริ่มจัดส่งเท่านั้นหรือไม่
2. ผู้ใช้ที่ได้รับเหรียญหรือรางวัลของแพ็กเกจเดิมแล้ว จะอัปเกรดได้หรือไม่
3. ถ้าผลสะสมเดิมมากกว่าเป้าหมายใหม่หลังอัปเกรด จะปลดล็อกรางวัลทันทีหรือรอการตรวจใหม่
4. ข้อมูลเดิมที่มีหลายใบสมัครใน Event เดียวกันจะคงไว้ ยกเลิก หรือรวมใบสมัครอย่างไร
5. ใบสมัครที่ Admin ปฏิเสธ (`failed`) กับผู้ใช้ยกเลิกเอง (`cancelled`) จะอนุญาตให้สมัครแพ็กเกจเดิมใหม่หรือไม่
6. ถ้างานปิดรับสมัครหลังผู้ใช้ยกเลิกแต่ก่อนสร้างใบสมัครใหม่ จะให้ Admin ช่วยคืนสถานะได้หรือไม่

## 10. แผนดำเนินงานในอนาคต

1. ตรวจข้อมูลจริงว่ามีผู้ใช้สมัครหลายแพ็กเกจใน Event เดียวกันจำนวนเท่าใด
2. ยืนยันกติกาเหรียญจริง เหรียญดิจิทัล รางวัล และการจัดส่ง
3. ออกแบบ Migration ใหม่และแผนรองรับข้อมูลเดิม
4. เพิ่มสถานะ Payment `cancelled`
5. เพิ่ม RPC ยกเลิกใบสมัครที่รอชำระ พร้อม row lock และ authorization
6. เพิ่ม RPC อัปเกรดงานฟรีและตารางประวัติ
7. เพิ่มกติกาหนึ่งใบสมัครที่ใช้งานอยู่ต่อ Event หลังจัดการข้อมูลเดิม
8. เพิ่มปุ่มและข้อความยืนยันในหน้าเว็บ
9. เพิ่มหน้า/ข้อมูลประวัติสำหรับผู้ใช้และ Admin
10. ทดสอบ RLS, RPC grants, transaction race และการเรียกพร้อมกัน
11. ทดสอบ Payment, BIB, ผลวิ่ง, Strava, เหรียญ รางวัล และการจัดส่งแบบ end-to-end
12. ทดสอบ TypeScript และ production build
13. รัน `docker compose up -d --build`, ตรวจ `docker compose ps` และ HTTP 200 ที่ `http://localhost:8025`
14. ใช้ Migration กับแต่ละ environment ตามลำดับและตรวจผลหลังใช้งานจริง

## 11. กรณีทดสอบขั้นต่ำ

- งานฟรี 10 กม. อัปเกรดเป็น 21 กม. โดยรักษาผลสะสมและ BIB เดิม
- งานฟรีพยายามลดจาก 21 กม. เป็น 10 กม. ต้องถูกปฏิเสธ
- งานฟรีพยายามเปลี่ยนไปแพ็กเกจของ Event อื่นต้องถูกปฏิเสธ
- งานเสียเงิน pending ยกเลิกเองแล้ว Registration และ Payment เป็น cancelled พร้อมกัน
- งานเสียเงิน pending เปลี่ยนแพ็กเกจแล้วได้ Payment ใหม่ที่ยอดตรงกับแพ็กเกจใหม่
- ผู้ใช้คนอื่นไม่สามารถยกเลิกหรืออัปเกรดใบสมัครที่ไม่ใช่ของตน
- Admin ยืนยันพร้อมกับผู้ใช้กดยกเลิก ต้องมีเพียงหนึ่งการเปลี่ยนสถานะที่สำเร็จและข้อมูลไม่ขัดกัน
- ใบสมัคร paid/confirmed ต้องอัปเกรดเองไม่ได้
- งานปิดหรือหมดเวลาต้องเริ่มการเปลี่ยนหรืออัปเกรดใหม่ไม่ได้
- ใบสมัคร cancelled ต้องสมัครใหม่ได้ตามนโยบายที่อนุมัติ
- รางวัล เหรียญ และ Shipment ต้องไม่ถูกสร้างซ้ำหลังอัปเกรด

## 12. ขอบเขตที่ยังไม่ทำในเอกสารนี้

- ยังไม่สร้าง Migration
- ยังไม่แก้ schema, RLS, RPC หรือ Storage policy
- ยังไม่แก้หน้าเว็บหรือ Server Action
- ยังไม่เพิ่มการชำระค่าส่วนต่างสำหรับงานเสียเงิน
- ยังไม่เปลี่ยนข้อมูลใบสมัครเก่า

เอกสารนี้ใช้เป็นฐานสำหรับทบทวนกติกาธุรกิจและจัดทำแผน Implementation ก่อนเริ่มแก้ระบบจริง
